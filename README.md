# Сервис валютных котировок

Тестовое задание на Go. Требования описаны в [task.md](task.md), архитектура и обоснования — в [choice.md](choice.md).

Сейчас реализованы пакеты `internal/config`, `internal/domain`, `internal/usecase`, `internal/logger`, определены интерфейсы `internal/repository` и подготовлен [OpenAPI-контракт](api/openapi.yaml). HTTP-адаптер, PostgreSQL-адаптер и Frankfurter реализованы; запуск приложения и воркеры ещё не реализованы. Ход разработки отслеживается в [roadmap.md](roadmap.md).

## Конфигурация

Для локальной разработки создайте `.env` из шаблона:

```sh
cp .env.example .env
```

`.env` исключён из Git. `.env.example` содержит демонстрационные параметры и предназначен для хранения в репозитории. Значения по умолчанию подходят для локальной разработки; `DATABASE_URL` необходимо передать явно.

Начальные параметры: 5 воркеров на экземпляр и общий лимит провайдера 2 запроса/с на все экземпляры, включая повторы. Это настройки приложения, а не опубликованная квота Frankfurter.

Пакет конфигурации вызывается из будущей точки входа приложения:

```go
cfg, err := config.Load(".env")
if err != nil {
    return err
}
```

В контейнере или другом окружении с уже заданными переменными используется `config.Load("")`. Явно указанный, но отсутствующий файл возвращает ошибку.

Приоритет: **переменные процесса → dotenv-файл → значения по умолчанию**. Пустое значение считается явно заданным и проходит обычную валидацию. Загрузка не меняет окружение процесса.

Конфигурация разделена на HTTP, PostgreSQL, воркеры и провайдер; также задаются уровень логирования и время завершения приложения. Длительности задаются с единицами, например `500ms`, `5s`, `30m`. Пакет проверяет типы, диапазоны и связанные ограничения, включая достаточную длительность lease. При ошибке конфигурация целиком отклоняется. Не логируйте структуру целиком: `Database.URL` может содержать пароль.

`config.Load` проверяет формат PostgreSQL URL. Полную проверку DSN, включая `sslmode`, выполняет pgx в `postgres.Open` до создания пула; `sslmode=enable` не является допустимым режимом. Ошибки должны сообщать о `DATABASE_URL`, не раскрывая строку подключения.

Для загрузки `.env` используется `github.com/joho/godotenv`; остальные операции пакета выполняются средствами стандартной библиотеки.

## Проверки

Для разработки и проверок используется **Go 1.25.2**. Директива `go` в `go.mod` задаёт минимальную версию; проверяйте фактический toolchain командой `go version`. Docker и CI будут использовать Go 1.25.2.

```sh
go test -race ./...
go vet ./...
```

Тестам конфигурации не нужны PostgreSQL, внешний API или локальный `.env`.

## Контракт API

[api/openapi.yaml](api/openapi.yaml) описывает API реализованных обработчиков; запуск приложения ещё не реализован.

| Операция | Назначение |
| --- | --- |
| `POST /v1/quote-updates` | Сохранить задание и вернуть ID после commit |
| `GET /v1/quote-updates/{id}` | Получить состояние и результат конкретного задания |
| `GET /v1/quotes/latest?pair=EUR%2FMXN` | Получить последний успешный результат пары |

Цена передаётся строкой. `updated_at` — время сохранения результата в UTC, `source_date` — дата дневного курса Frankfurter/ECB. Latest выбирается по дате источника, затем времени сохранения и ID. Неудача нового обновления не удаляет предыдущую успешную котировку.

Необязательный `Idempotency-Key` содержит 1–128 печатных ASCII-символов без пробелов. Повтор ключа с той же парой возвращает прежний ID; другая пара даёт `409`. При повторе активного задания возвращается `202`, терминального — `200`. Все эти POST-ответы содержат только ID и статус; результат читается по `Location`. Автоматическая очистка заданий и ключей пока не предусмотрена, срок хранения будет определён отдельно.

Проверка спецификации в отдельном Python-окружении:

```sh
python3 -m venv /tmp/quotes-openapi-check
/tmp/quotes-openapi-check/bin/python -m pip install openapi-spec-validator==0.7.2
/tmp/quotes-openapi-check/bin/python -m openapi_spec_validator api/openapi.yaml
```

## Логирование

`internal/logger` предоставляет `Debug`, `Info`, `Warn`, `Error` и `With` поверх `log/slog`. Формат — JSON; `nil` вместо writer выбирает stdout. Поле `service` добавляется при непустом имени, `With` создаёт дочерний логгер без изменения родителя. Глобальный `slog.Default()` не изменяется.

В будущей точке сборки `cmd/quotes`, после успешного `config.Load`, создайте логгер:

```go
log := logger.New(cfg.LogLevel, "quotes", os.Stdout)
httpLog := log.With("component", "http")
workerLog := log.With("component", "worker")
```

`httpLog` и `workerLog` передаются через конструкторы будущим HTTP- и worker-компонентам. Воркер может получить дочерний логгер с `update_id`, `pair` и `attempt` для конкретной попытки. Ошибку логируйте один раз на границе обработки; домен и интерфейсы repository не получают логгер. Текущие сценарии usecase могут возвращать обёрнутые ошибки без логирования. Если появятся самостоятельные прикладные события, задайте нужный интерфейс рядом с usecase и передайте его реализацию через конструктор; конкретный `slog.Logger` туда не требуется.

Точки входа и запускаемых адаптеров пока нет: это пример подключения, а не уже работающий запуск сервиса. Связка с `Config.LogLevel` проверяется исполняемым примером `ExampleNew` в тестах logger. В тестах вывода вместо stdout передаётся `bytes.Buffer`.

Не передавайте в логи DSN, конфигурацию целиком и ключ идемпотентности: логгер не выполняет автоматическое удаление секретов. Ошибки с исходными данными не отправляются клиенту напрямую.

Проверки проекта:

```sh
go test -race ./...
go vet ./...
```

## Локальная PostgreSQL и миграции

Compose использует PostgreSQL `17.6-bookworm` и отдельный инструмент
`golang-migrate` `v4.18.3`. Это локальное окружение, а не HA-кластер.
Переменные `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT`
описаны в `.env.example`; при их отсутствии используются те же локальные значения.
`DATABASE_URL` приложения должен соответствовать этим настройкам. Внутри Compose
мигратор обращается к хосту `postgres`, приложение на машине — к `localhost`.
Пароль мигратор получает через `PGPASSWORD`, не через аргумент URL.

```sh
make db-up
make migrate-up
make migrate-version
```

Повторный `make migrate-up` не применяет уже выполненные миграции.
Миграции запускаются отдельным шагом до приложения, не через
`docker-entrypoint-initdb.d`. Каждый SQL-файл выполняется в явной транзакции.
Не редактируйте уже применённые миграции: изменения схемы оформляйте новой версией.
Для rolling update сначала добавляйте совместимые поля, а удаляйте старые
отдельной миграцией после обновления всех экземпляров приложения.

`make migrate-down` откатывает **одну** миграцию и удаляет соответствующую таблицу
с данными. `make db-stop` останавливает БД, сохраняя именованный volume.
Изменение переменных пользователя/пароля не меняет учётные данные в уже
инициализированном volume.

Проверка ограничений на отдельной тестовой БД (не использует личный `.env`):

```sh
export POSTGRES_PORT=15439
docker compose --env-file .env.example -p quotes-migration-check up -d --wait postgres
docker compose --env-file .env.example -p quotes-migration-check run --rm migrate up
docker compose --env-file .env.example -p quotes-migration-check exec -T postgres \
  psql -U quotes -d quotes -v ON_ERROR_STOP=1 < tests/postgres/constraints.sql
```

SQL-проверки откатывают свои данные. Для удаления только этого тестового окружения:

```sh
docker compose --env-file .env.example -p quotes-migration-check down -v
```

Проверки PostgreSQL-адаптера на отдельной тестовой БД с применёнными миграциями:

```sh
TEST_DATABASE_URL='postgres://quotes:quotes_local@localhost:15439/quotes?sslmode=disable' \
  go test -tags=integration -race ./internal/repository/postgres -count=1 -v
```

Тест проверяет запрос через возвращённый пул, лимит соединений, таймаут ожидания
занятого пула и его работоспособность после таймаута. Сам тест Open не требует таблиц, но общий запуск интеграционных тестов требует миграций.
Без тега `integration` этот файл не включается в тесты; с тегом отсутствие
`TEST_DATABASE_URL` считается ошибкой настройки.

Интеграционные тесты repository требуют применённых миграций и **отдельной тестовой БД**: они очищают `quote_updates` через `TRUNCATE`. Не задавайте `TEST_DATABASE_URL` на рабочую БД. Проверяются конкурентная идемпотентность, предел очереди, чтение состояний и порядок latest. Перед запуском примените миграции в том же тестовом Compose-проекте.

## HTTP-адаптер

Пакет `internal/transport/httpapi` реализует маршруты OpenAPI. `httpapi.New(service, log).Routes()` возвращает `http.Handler`; запуск сервера в `main` пока не реализован. Обработчики тестируются через `httptest` с фейком сервиса без БД и сети. Тело POST ограничено 4096 байтами; ответы не раскрывают ошибки драйвера. Неизвестный путь возвращает JSON 404, неверный метод — JSON 405 с Allow.

## Адаптер Frankfurter

`internal/provider/frankfurter` реализует `usecase.QuoteProvider`. Конструктор `frankfurter.New(baseURL, timeout)` создаёт переиспользуемый HTTP-клиент. `Fetch(ctx, pair)` выполняет одну попытку и возвращает `domain.Quote`; источник — `frankfurter:ecb`. Ошибки `usecase.ProviderError` содержат категорию, признак возможности повтора и RetryAfter, сохраняя причину через Unwrap. Отмена родительского контекста возвращается отдельно. Ответ ограничен 64 KiB, редиректы отключены, цена читается без float64. Повторы, общий лимит RPS и circuit breaker будут реализованы в следующих этапах. Тесты используют только локальный httptest.Server.

Исправления аудита E01–E05 покрыты регрессионными тестами: RateLimited для 429, запрет неоднозначных JSON-полей, read-only PostgreSQL → 503 и проверка публичного source. Воркеры, общий limiter/breaker, исполняемое приложение и HA-испытания остаются открытыми.
